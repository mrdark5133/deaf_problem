# HAND-SIGN ACCURACY PROMPT — paste into Antigravity (Planning mode)

You are the lead engineer on **SignBridge** (repo `mrdark5133/deaf_problem`). The avatar's hand signs do not look accurate. Your job is to find out **why**, fix what is fixable in code, and get **real** sign data into the library. Do not guess: measure first.

## Read first (mandatory)
`rules.md`, `plan.md`, `task.md`, `docs/limitations.md`, `reports/phase-3-report.md`, `reports/phase-4-report.md`, `data/signs/index.json`, the `scripts/` folder, and the code in `frontend/src/recorder/` and `frontend/src/player/`.
All rules in `rules.md` apply, **including the Phase Gate Protocol and honesty rules**. Work in phases H0–H3; after each, test, write `reports/hand-<H#>-report.md`, and STOP for my `approve`.

## Known facts (verify them, don't assume)
- The Phase 3 report says the library is **96 synthetic clips and 0 real clips**. Synthetic clips are generated by a script and are **not real signs**, so hand shapes cannot be accurate no matter how good the renderer is.
- Clips are 2D-normalized landmarks. A 2D view loses finger detail when fingers point toward the camera (foreshortening), so even real clips can look wrong.
- Possible pipeline problems to check: over-smoothing that flattens finger movement, blending that distorts hand shape during a hold, wrong left/right hand assignment, hand scale tied to body scale, mirrored handedness, and clip trimming that cuts the sign.

## Hard rules
1. Never present synthetic clips as accurate signs. Report real vs synthetic counts in every report.
2. Every fix must be justified by a measurement or a screenshot from H0. No speculative tuning.
3. Do not download datasets or copy third-party code. Follow `import-data-prompt.md` rules (license gate, provenance fields, no raw data in git) for any external data.
4. Keep existing tests green; add regression tests for every fix.

## Phases

### H1 — Pipeline fixes (evidence-based only)
Fix only what H0 proved. Likely candidates:
- **Per-part smoothing:** lighter filtering for fingers than for arms; keep it from flattening handshapes; make the parameters configurable.
- **Blend only transitions:** do not blend the hand pose during the hold phase of a sign; hold the recorded handshape and ease only in/out.
- **Hand scale:** normalize hand size separately from body scale so finger proportions stay consistent.
- **Hand assignment/mirroring:** fix any left/right mixups with the wrist-proximity rule; add a mirror option for left-handed signers.
- **Trim tuning:** stop cutting the start/end of signs; keep a small margin.
- **Tests:** a fixture clip with expected metrics (finger-length variation, jitter) and thresholds; hand-assignment tests; blend tests proving the hold segment is unchanged.
- **Accept:** H0 metrics improve measurably (report before/after numbers) and screenshots show clearer hands.
- 🛑 STOP and ask to approve H2.

### H2 — Real sign data
- Write `docs/recording-protocol.md`: lighting from the front, plain background, camera at chest height about 1 m away, both hands and the face in frame, start and end in a rest pose, normal signing speed, sleeves that contrast with skin, 3 takes per sign, keep the best, right-hand-dominant signer (or use the mirror option). Include a per-sign checklist table for the demo-critical signs (start with 15–20 from the three demo scripts).
- Add a **clip quality score** (missing-hand-frame ratio, jitter, duration plausibility, hand-in-frame) shown in `/recorder` and `/import-review`, with a red/amber/green verdict and a reject threshold.
- If I approve an external keypoint or video dataset, import it with the phases in `import-data-prompt.md` (D0–D1b), with license confirmation first.
- Report **real vs synthetic** counts and coverage of the demo scripts using real clips only.
- **Accept:** at least the agreed demo-critical signs are real and pass the quality gate; anything still synthetic is clearly flagged in the UI and reports.
- 🛑 STOP and ask to approve H3.
